## 1. Executive Summary

This comprehensive, read-only audit was performed across the entire Royal Wellness Center WhatsApp CRM codebase to identify all sources of unnecessary Supabase egress (data transfer), excessive query execution, and storage bandwidth consumption.

### Key Takeaway
The application does **not** consume bandwidth via Supabase Realtime subscriptions (realtime is handled by an internal Node.js SSE server). Instead, **over 85% of Supabase egress is generated by continuous short-interval polling of PostgreSQL database tables from frontend clients through the Node.js backend**, compounded by:
1. **Unconditional 4-second background message polling** (`GET /api/messages?paginate=1&limit=50`) running continuously in every coordinator browser tab.
2. **Redundant message joins** (`include: { messages: true }`) on lead updates, assignments, and unassignments that pull hundreds of historical messages across the wire for simple status changes.
3. **Binary media persistence directly inside Supabase PostgreSQL as `BYTEA` blobs** (`public.media_files`) rather than using Supabase CDN storage, causing multi-megabyte media files to be transferred over the database connection pooler.
4. **Short-lived signed URLs (15-minute TTL)** that bust browser HTTP caches, forcing repeat requests for previously cached images and audio.
5. **Unbounded queries without pagination or date boundaries** on appointments (`GET /api/appointments`) and 30-second polling on exam handoff records (`GET /api/exam-ops/handoffs`).

By addressing these architectural inefficiencies, the CRM can achieve an estimated **70% to 85% reduction in Supabase database egress and network round-trips** without modifying database schemas, altering WhatsApp webhook behavior, or impacting coordinator workflows.

### Connectivity Characteristics
- **Client to Backend:** Frontend does **not** import `@supabase/supabase-js`. All client requests route through the backend API (`/api/*`) authenticated with HMAC-SHA256 bearer tokens.
- **Backend to Supabase:** The backend connects using `@prisma/client` with `@prisma/adapter-pg` over the Supabase transaction pooler (`aws-0-ap-northeast-2.pooler.supabase.com:6543/postgres?pgbouncer=true`).
- **Real-time Pipeline:** Handled by a Node.js SSE stream (`/api/events`), broadcasting events like `INBOUND_WHATSAPP_MESSAGE`, `OUTBOUND_WHATSAPP_MESSAGE`, `LEAD_ASSIGNED`, and `LEAD_UPDATED`.

## 7. Recommended Optimizations (Phase-by-Phase)

### Priority 1: High Impact (Immediate Database Bandwidth Relief)

#### Recommendation 1.1: Replace Aggressive 4-Second Polling with Adaptive / Event-Driven Sync
- **Current Problem:** Client calls `syncLatestMessages()` every 4,000ms unconditionally.
- **Proposed Solution:**
  - Rely on the active SSE connection (`/api/events`), which already broadcasts `INBOUND_WHATSAPP_MESSAGE` and `MESSAGE_STATUS_UPDATE` instantly.
  - Demote background polling from 4 seconds to an adaptive fallback (e.g. 60–120 seconds, or execute only when the browser tab regains focus via `document.visibilityState === 'visible'`).
  - Keep `syncLatestMessages()` on initial load and upon SSE reconnection (`eventSource.onopen`).
- **Files Affected:** `frontend/src/context/CrmContext.tsx`

#### Recommendation 1.2: Remove `messages: true` from Lead Update and Assignment Operations
- **Current Problem:** `prisma.lead.update` and `prisma.lead.findUnique` include all messages on unassignment (line 4421), assignment (lines 4578, 4600), updates (line 4886), and creation (line 5303).
- **Proposed Solution:**
  - Remove `messages: { orderBy: { timestamp: 'asc' } }` from the `include` block of these mutation endpoints.
  - Replace with `_count: { select: { messages: true } }` if message counts are required by badges.
  - The client already maintains conversation history in state and fetches messages independently via `/api/messages?leadId=...`.
- **Files Affected:** `backend/src/legacyServer.js`

#### Recommendation 1.3: Migrate Media to Supabase Storage Bucket with CDN Caching
- **Current Problem:** Media is stored in PostgreSQL table `public.media_files` as `BYTEA` blobs when `SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY` are not configured.
- **Proposed Solution:**
  - Ensure `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, and `SUPABASE_MEDIA_BUCKET` are populated in production configuration.
  - Serve media through Supabase Storage public CDN or direct signed URLs with standard asset caching, rather than proxying multi-megabyte binary data over the PostgreSQL database connection pooler.
- **Files Affected:** `backend/src/supabaseMedia.js`, `backend/src/legacyServer.js`

---

### Priority 2: Medium Impact (Query Efficiency & Cache Retention)

#### Recommendation 2.1: Extend Signed Media URL Validity or Use Deterministic Token Signature
- **Current Problem:** 15-minute expiration timestamp causes URL query string to change on every message refresh, breaking browser HTTP caching.
- **Proposed Solution:**
  - Align media signatures with long-lived session windows (e.g., 24 hours or HMAC of filename + secret without millisecond-level expiry jitter).
  - This allows the browser's disk cache to satisfy repeat image/voice note requests without hitting the server or Supabase.
- **Files Affected:** `backend/src/legacyServer.js`

#### Recommendation 2.2: Add Date Range Boundaries to Pipeline Appointments Query
- **Current Problem:** `TableView.tsx` mounts and requests `GET /api/appointments` with empty parameters, querying every appointment ever booked.
- **Proposed Solution:**
  - Scope the Leads table appointment lookup to active/upcoming time windows (e.g., current month or appointments associated with visible paginated leads via `patientId in (...)`).
  - Add a server-side default `LIMIT 200` to prevent unbounded SQL execution.
- **Files Affected:** `frontend/src/components/leads/TableView.tsx`, `backend/src/appointmentRoutes.js`

#### Recommendation 2.3: Push Filters Down to SQL in Exam Handoffs and Leads Queries
- **Current Problem:** `examOperations.js` queries 500 rows and filters by `assignedOfficerId` in Node.js memory. Lead queries fetch 200 rows and filter by `company` in Node.js memory.
- **Proposed Solution:**
  - Add `WHERE data->>'assignedOfficerId' = user.id` in `examStore.js` SQL query for non-managers.
  - Add `company` directly to Prisma `whereClause` in `/api/leads`.
- **Files Affected:** `backend/src/examStore.js`, `backend/src/legacyServer.js`

---

### Priority 3: Low Impact (Frontend Resource Polish)

#### Recommendation 3.1: Enable Lazy Loading for Images & Remove Audio Preload
- **Current Problem:** Long chat threads immediately request all images and fetch audio metadata for every voice note.
- **Proposed Solution:**
  - Add `loading="lazy"` to `<img>` in `MessageBubble.tsx`.
  - Set `preload="none"` on `<audio>` in `WhatsAppVoiceNotePlayer.tsx`, loading audio data only when the coordinator clicks Play.
- **Files Affected:** `frontend/src/components/chat/MessageBubble.tsx`, `frontend/src/components/chat/WhatsAppVoiceNotePlayer.tsx`
